# 1 项目概述

## 1.1 项目背景

在数字经济与产业升级双轮驱动的时代背景下，大学生就业问题已从单一的人才输送命题，演变为检验教育适配性、技术前瞻性和社会协同性的复杂系统工程。一方面，智能制造、人工智能等战略新兴产业面临大量人才缺口；另一方面，传统专业毕业生结构性失业问题凸显。这种"岗位荒"与"就业难"并存的现象，暴露了就业能力和社会经济发展需求之间的供需不匹配。

高校毕业生规模持续攀升。据教育部统计，2025年全国高校毕业生人数已突破1200万，就业市场竞争日益激烈。在当前大学生职业规划与求职过程中，学生普遍面临多方面的现实困境，这些问题不仅影响求职效率，也直接制约就业质量。从表层表现看，这些困难体现在信息获取、经验表达和决策执行等多个环节；从本质上看，则源于学生侧能力认知与岗位侧能力要求之间缺乏有效对齐机制。

综合调研与实际观察，相关问题可归纳为以下四个方面：

（1）自我认知不清，缺乏清晰能力画像。多数学生在专业选择和职业规划过程中，受分数、外部建议等因素影响较大，缺乏对自身兴趣、能力与发展方向的系统性认知。在求职阶段，难以将已有的学习与实践经历转化为结构化的能力表达，导致职业选择具有较强盲目性。

（2）岗位信息碎片化，能力要求难以理解。当前岗位信息多来源于招聘平台或社交媒体，呈现出碎片化、非结构化特征。学生难以从职位描述中准确提炼关键能力要求，也缺乏对岗位发展路径与行业演进的整体认知，从而难以建立清晰的职业参照体系。

（3）个性化指导不足，缺乏持续支持机制。高校职业规划课程多以通用性指导为主，难以覆盖不同专业与岗位的差异化需求；同时，现有招聘平台（如BOSS直聘、智联招聘）主要提供岗位信息与投递服务，缺乏针对求职者能力提升与长期发展的深度支持，难以形成持续性的指导体系。

（4）规划与行动脱节，缺乏闭环机制。学生在制定职业目标后，往往缺乏明确的阶段任务拆解与反馈机制，难以将规划转化为具体行动；在求职受挫时，也缺乏基于实际结果进行调整与优化的能力，导致规划难以持续迭代。

综上所述，大学生职业规划问题的核心，不仅在于信息不足或经验欠缺，更在于缺乏一套能够将“个人能力”与“岗位需求”进行结构化对齐的系统性工具。因此，有必要构建一个以能力画像为基础、以人岗匹配为核心、以行动闭环为导向的智能化职业规划智能体，帮助用户清晰定位自身能力、系统化推进求职准备，从而提升就业质量与求职效率，从根本上提升职业决策的科学性与可执行性。

## 1.2 项目定位

### 1.2.1 应用场景

"职点迷津"定位为面向大学生群体的AI职业规划与求职导航系统，核心应用场景包括：

场景一：从岗位信息出发，理解职业选择方向。用户在浏览或输入目标岗位后，系统将分散的岗位描述转化为结构化能力要求，并呈现岗位之间的晋升路径与横向迁移关系。用户可以直观查看“从入门到资深”的发展轨迹，以及不同岗位之间的能力共通性，从而将单一职位理解为一条可选择的职业路径，而非孤立信息。

场景二：整理自身经历，形成清晰的能力认知。用户上传简历或补充项目与学习经历后，系统自动将其拆解为专业技能、通用能力、实践经历与成果表现等维度，并生成可视化能力画像。用户可以清楚看到自身能力的完整度与相对竞争力，明确已经具备什么能力，以及还缺少哪些关键能力。

场景三：基于匹配结果制定具体行动计划。系统会基于个人能力画像与岗位能力画像进行匹配分析，从技能、经验与潜力等多个维度给出可解释的差距说明，并进一步生成职业发展报告，包含阶段性目标、学习路径与实践建议，使用户能够将职业规划转化为可执行的行动步骤。

场景四：围绕项目与材料进行持续优化与表达提升。用户可以上传项目文档、代码仓库或相关材料，形成用户自己的知识库储备，与系统进行对话式交互。系统自动检索相关内容并辅助用户梳理项目逻辑、提炼技术亮点与优化表达方式，使用户能够将零散经历转化为结构清晰、表达清晰的项目叙述，并用于简历或面试准备。

### 1.2.2 目标人群

本项目以**普通高等学校全日制在校生**为主力用户，覆盖从低年级建立认知到毕业学年集中求职的全周期；按准备深度划分为四档服务侧重，提供差异化的服务：


| 阶段  | 名称    | 用户特征           | 智能体平台服务重点        |
| --- | ----- | -------------- | ---------------- |
| 阶段一 | 认知建立期 | 低年级学生，尚未明确职业方向 | 岗位探索、能力认知启蒙、知识沉淀 |
| 阶段二 | 能力构建期 | 有一定课程/项目经验     | 项目解析、能力画像构建      |
| 阶段三 | 决策准备期 | 面临实习/求职选择      | 人岗匹配、简历定制、职业规划   |
| 阶段四 | 行动优化期 | 已进入投递或面试阶段     | 面试模拟、报告优化与复盘     |


## 1.3 项目方案

“职点迷津”项目面向大学生职业规划与求职决策场景，以大语言模型为核心引擎，融合向量检索、RAG与Agent技术，构建一个覆盖“岗位认知—能力评估—匹配决策—行动规划—持续优化”的智能职业规划闭环系统。

系统整体以用户职业决策流程为主线，将复杂的求职过程拆解为四个相互衔接的核心模块：

1. 岗位认知与能力画像构建模块：系统基于岗位数据集对招聘信息进行结构化处理，提取岗位核心能力要求，构建标准化岗位能力画像，并建立岗位之间的纵向发展路径与横向迁移关系图谱。同时支持用户通过简历上传或信息录入方式构建个人能力画像，将非结构化经历拆解为专业技能、实践经验与综合素养等维度，并输出能力完整度与岗位竞争力评估结果，为后续决策提供基础依据。
2. 个人知识库与项目能力解析模块：系统支持用户上传项目文档、课程资料及GitHub代码仓库等多源信息，通过文本分块与向量化处理构建个人知识库。在此基础上，结合大语言模型对项目进行结构化解析，从技术栈、个人贡献与业务价值等维度提取关键信息，辅助用户优化项目表达，并支持基于上下文的持续问答与深度分析。
3. 人岗匹配与职业规划生成模块：在岗位能力画像与个人能力画像对齐基础上，系统通过语义向量匹配与规则加权模型计算人岗契合度，从技能匹配、经验匹配与发展潜力等维度生成可解释分析结果。基于匹配结果与用户职业意向，系统进一步生成个性化职业发展方案，包括目标岗位选择、发展路径规划以及分阶段行动计划，并支持自动生成定制化简历输出。
4. AI对话驱动的持续优化模块：系统提供基于用户个人知识库与岗位信息的AI对话能力，在交互过程中动态检索相关文档与代码片段，实现上下文增强生成。用户可围绕项目经历、职业选择及面试准备进行多轮对话，系统持续优化表达内容与求职策略，形成“反馈—优化—再决策”的闭环机制。

## 1.4 项目目标

本项目围绕“基于AI的大学生职业规划智能体”赛题要求，从业务价值、系统能力、工程实现与效果评估四个维度构建目标体系，确保系统具备实际应用价值与可验证性。

- 业务目标：降低职业决策信息不对称。

系统面向大学生在职业规划过程中普遍存在的自我认知不足、岗位信息碎片化与路径不清晰等问题，构建统一的能力表达与岗位理解体系，帮助用户从“模糊选择”转向“结构化决策”，提升职业选择的科学性与匹配效率。

- 能力目标：构建可解释的岗位/学生画像分析与职业规划系统

系统需具备以下核心能力：构建就业岗位要求画像，并建立岗位间的关联图谱（包括垂直岗位和换岗路径）；构建学生就业能力画像，分析学生竞争力；构建学生职业生涯发展报告，通过岗位画像和就业能力画像进行人岗匹配，分析学生优势与不足；为学生制定职业目标，构建职业发展路径和成长计划建议。实现岗位侧与用户侧在统一语义空间下的解释对齐。

- 工程目标：实现LLM驱动的可落地系统架构

统以大语言模型为核心能力引擎，结合向量检索、RAG与Agent机制，实现以下工程能力：支持非结构化数据（简历、岗位等信息）解析；支持实时人岗匹配与结果生成；支持职业规划报告自动生成与导出；支持个人知识库构建与检索。确保系统具备可部署性、可扩展性与模块化设计能力。

- 评估目标：构建可量化的效果验证体系

为保证系统结果的可靠性与实用性，本项目设置如下评估指标：人岗匹配的关键技能匹配准确率不低于80%；岗位画像与学生画像的关键信息准确率需超过90%；职业规划的反馈结果对学生有实际指导意义。

## 1.5 项目价值

“职点迷津”项目围绕大学生职业规划与求职决策场景，基于AI技术构建能力画像与人岗匹配系统，在社会价值、用户价值、商业价值与技术价值等层面具有一定意义。

### 社会价值：缓解就业结构性矛盾，提升就业质量

当前就业市场中，“岗位需求与人才供给不匹配”已成为突出问题。本项目通过构建标准化岗位能力画像与学生能力画像，实现供需双方在能力维度上的结构化对齐，有助于缓解信息不对称问题，减少盲目投递与无效竞争。

同时，系统将职业规划从一次性决策转变为持续优化过程，使学生能够在学习阶段逐步积累与岗位需求相匹配的能力，从源头提升就业质量。这对于高校就业指导体系的数字化升级与精细化服务具有积极意义，也有助于促进人才培养与产业需求的协同发展。

### 用户价值：降低求职门槛，提升决策效率与质量

对于大学生用户而言，本项目的核心价值在于将复杂的求职过程转化为结构化、可执行的决策流程：通过岗位画像与路径图谱，降低信息理解成本，帮助用户快速理解行业与岗位要求；通过能力画像与量化评分，提升能力认知清晰度明确自身优势与不足；通过职业规划报告与行动路径，强化决策可执行性，将目标转化为具体步骤。

### 商业价值：拓展智能招聘与教育服务应用场景

本项目具备向多个行业场景延伸的潜力：在招聘领域，可作为招聘平台的智能匹配增强模块，提高岗位推荐准确性与筛选效率；在教育领域，可服务高校就业指导中心，作为职业规划辅助工具，实现个性化指导；在职业培训领域，可结合能力差距分析，提供精准课程推荐与能力提升路径

通过与招聘平台、高校及培训机构合作，项目具备形成“数据+服务”一体化解决方案的商业化潜力。

### 技术价值：验证大模型在复杂决策场景中的应用范式

本项目将大语言模型、向量检索与RAG技术应用于“多对象对齐 + 决策生成”场景，具有以下技术探索价值：非结构化数据（简历、岗位、项目）的结构化抽取与统一表示；构建“岗位画像—用户画像—匹配分析”多层语义对齐机制；探索 Agent 开发在多步骤职业规划任务中的应用。

# 2 开发计划

## 2.1 最终呈现形式

本系统以 **基于浏览器的 Web 应用** 作为最终交付形态。系统采用 **前后端分离** 架构：前端以单页或模块化方式实现主要业务界面，通过标准接口与后端交互；用户无需安装独立客户端，可在桌面端与移动端浏览器中完成账户管理、简历与能力信息维护、岗位信息浏览与能力说明查阅、职业生涯报告生成与导出、智能对话及个人知识库使用等操作。界面采用**响应式布局**，保障常见桌面分辨率与主流移动设备视口下的可读性与可操作性。

## 2.2 主要功能描述

### 核心功能

核心功能对应赛事题目中的“双画像构建—人岗匹配—发展报告—编辑导出”主线，具体包括：

1. **账户与安全**：提供用户注册、登录及会话管理能力，实施权限控制，确保个人履历、测评结果与对话记录等数据仅对本人可见。
2. **岗位信息与岗位侧能力说明**：支持岗位数据检索与详情查看；在原始招聘信息基础上，利用大语言模型归纳形成结构化的 **就业岗位要求说明**（含核心技能、职责侧重等），并持久化存储，支持多次对比与复盘。
3. **岗位关系与职业发展路径**：系统已在岗位数据基础上完成 **纵向晋升** 与 **横向换岗** 关联关系构建，形成可浏览、可查询的发展与迁移路径；路径覆盖范围已满足赛事对岗位数量及换岗路径条数的最低要求。
4. **简历与经历结构化维护**：支持教育背景、任职经历、项目实践与技能等信息的分类录入与维护，为能力画像与人岗匹配提供一致、可追溯的数据基础。
5. **学生就业能力画像**：支持自上传文件解析或文本录入等方式生成画像；输出专业技能、通用素养等多维度要素，并给出 **能力完整度、竞争力** 等量化评价，支持重复生成与迭代更新。
6. **人岗匹配与结果解释**：在岗位侧与学生侧信息对齐的前提下，从基础要求、职业技能、职业素养与发展潜力等维度开展对比与加权，输出 **可解释的匹配结论与差距分析**。
7. **职业生涯发展报告**：系统已实现职业探索、目标设定、发展路径与短中期行动计划的自动生成，并提供评估或复盘节奏；支持内容润色、完整性校验、人工修订与 **一键导出**。
8. **智能对话与知识增强**：提供多轮职业相关对话；结合个人知识库语义检索，在回答中融合与岗位及项目材料相关的上下文，提高回答针对性。

### 次要功能与支撑能力

次要功能用于保障系统可用性、体验与工程可维护性，包括：个人知识库的文档入库、异步向量化与检索；附件与对象存储管理；热点数据与验证码等场景的缓存策略；健康检查、日志与基础监控等运维支撑。次要功能 **不替代** 上述核心闭环的交付要求。

## 2.4 验收标准

## 2.5 关键问题

1. **模型效果与评测复现**：大语言模型输出存在随机性，须建立 **版本化提示词与后处理规则**，并配套 **固定抽样评测集与双人交叉标注**，确保 A1、A2 指标可重复验证。
2. **岗位数据与图谱建设**：万级岗位与百级岗位类型的清洗、导入及路径建模工作量较大，须提前锁定 **数据字典、导入脚本与图谱展示形态**，避免后期结构性返工。
3. **调用成本与响应时间**：画像、报告、嵌入与对话均依赖外部智能服务，须通过缓存、异步任务、批量请求等手段控制 **单次演示与全赛程** 的综合费用及 P1、P2 指标达标。
4. **个人信息保护**：简历与测评数据属敏感信息，须在传输加密、访问鉴权、日志脱敏与备份策略上满足 **最小必要** 原则。
5. **接口契约与联调效率**：前后端接口、错误码与鉴权方式须在 **详细设计阶段** 冻结，降低集成阶段返工风险。
6. **外部依赖降级**：当大模型或对象存储不可用时，系统须返回 **可理解错误信息** 并避免界面长时间无响应。
7. **报告导出定版**：报告导出格式与版式须在 **验收前两周** 冻结，确保演示视频与纸质材料一致。

# 3 可行性分析

## 3.1 技术可行性分析

本项目所采用的各项技术均为业界成熟且广泛应用的技术方案，技术可行性高。
后端框架：主服务采用 Java + Spring Boot ，生态成熟，具备完善的安全、数据访问与运维支持。AI 能力统一集成在**Spring AI**，通过 **Spring AI Alibaba** 的 DashScope Starter 接入通义千问对话与向量模型，避免维护独立的 Python 推理服务。
大语言模型与对话：采用通义千问（Qwen）系列。业务侧使用 Spring AI 的 `ChatModel` / `ChatClient` 完成同步与流式对话；会话记忆通过 `spring-ai-starter-model-chat-memory-repository-jdbc` 落库至 PostgreSQL（`MessageWindowChatMemory` 等），与业务数据同源存储，便于部署与运维。
向量检索与 RAG：向量存储与相似度检索采用 **PostgreSQL + pgvector**，嵌入模型通过 Spring AI 的 `EmbeddingModel`（DashScope 侧配置）生成；知识库文档经分块后写入向量表，对话检索与上下文拼装由 `KnowledgeRagService` 等 Java 服务完成，检索策略（如查询改写、Top-K、上下文长度预算）由应用配置与代码协同控制。
文档处理：项目文档（PDF 等）正文抽取采用 **Apache Tika**（`tika-core` / `tika-parsers-standard-package`）；文本分块采用 Spring AI 自带的 `**TokenTextSplitter`** 等切分器，与向量化流水线同进程执行。知识库文档类型在业务模型中区分项目文档、纯文本、GitHub 链接等，**当前向量化实现已覆盖项目文档（PDF 链接）路径**，其余类型可按同一套 Spring AI 嵌入与存储接口扩展。
容器化部署：采用 Docker 多阶段构建和 Docker Compose 编排，配合 GitHub Actions 实现 CI/CD 自动化部署，确保开发到生产的流程高效可控。

# 4 需求分析

## 4.1 数据需求

### 4.1.1 静态数据

静态数据指在系统运行过程中相对稳定、不频繁变化的数据，主要用于支撑岗位认知与能力建模，包括：

1. 岗位基础数据：来源于公开招聘数据集，包含职位名称、工作地址、薪资范围、公司全称、所属行业、人员规模、企业性质、职位编码、职位描述、公司简介等字段。该类数据为构建岗位能力画像的基础输入。
2. 岗位能力画像数据：基于岗位描述经大语言模型抽取与归纳形成的结构化能力信息，包括专业技能、证书要求、创新能力、学习能力、抗压能力、沟通能力、实习能力等维度。该数据用于后续人岗匹配与路径分析。
3. 岗位关联与路径数据：描述岗位之间的纵向晋升关系（如UI/视觉设计师 - 资深体验设计组长 - 设计总监/创意总监）与横向迁移关系（如后端开发→数据工程师），用于构建职业发展路径图谱
4. 能力维度标准定义：统一定义系统中使用的能力分类体系（如基础要求、职业技能、职业素养、发展潜力），保证岗位画像与学生画像在同一语义体系下对齐。

### 4.1.2 动态数据

动态数据指在用户使用过程中实时产生或频繁更新的数据，主要包括：

1. 用户基本信息与账户数据：包括用户注册信息（邮箱、密码）、登录状态、权限控制信息等。
2. 学生能力画像数据：由用户上传简历、填写信息或导入项目资料后，经系统解析生成的结构化能力数据，包括技能、项目经验、实践经历及能力评分等（完整度、竞争力等）。
3. 简历与项目数据：用户维护的教育背景、实习经历、项目经历、技能列表等信息。
4. 人岗匹配结果数据：系统基于岗位画像与学生画像生成的匹配分析结果，包括各维度评分（基础要求、职业技能、职业素养、发展潜力）、综合评分及差距说明。
5. 职业发展报告数据：系统生成的个性化职业规划报告，包括职业目标、发展路径、阶段性任务与评估建议，支持用户修改与版本更新。
6. 知识库与向量数据：用户上传的文档（PDF、Markdown等）及GitHub仓库内容，经分块与向量化处理后形成的语义索引数据，用于RAG检索增强。
7. 对话与交互数据：用户与AI系统的对话记录，包括问题、上下文信息、模型回复内容等，用于支持多轮对话与上下文记忆。

### 4.1.4 数据采集

系统数据来源与采集方式如下：

（1）岗位数据采集
来源：竞赛提供数据集或公开招聘平台数据
方式：离线导入 + 批量清洗处理
频率：初始化导入为主，可按需扩展更新

（2）用户数据采集
来源：用户注册、表单填写、简历上传
方式：前端表单提交 + 文件解析（PDF/文本）
频率：按用户操作实时更新

（3）项目与知识库数据采集
来源：用户上传文档或关联GitHub仓库
方式：文件解析 + 分块处理 + 向量化存储
频率：按上传触发，异步处理

（4）模型生成数据
来源：大语言模型推理结果（岗位画像、能力画像、匹配分析、报告生成）
方式：API调用 + 结果结构化存储
频率：按业务请求触发

（5）对话与日志数据
来源：用户与系统交互过程
方式：实时记录并存储
频率：实时生成

为保证数据质量与系统性能，数据采集过程需结合数据校验、去重处理与异步任务机制，确保系统在并发与大数据量场景下的稳定运行。

## 4.3 性能需求

本节规定系统在 **响应时间、吞吐与并发、资源占用** 等方面的目标，与 **§2.4 验收标准** 中“性能与体验”及“稳定性”条目一致；测试与验收以同区域部署、无蓄意压垮外部服务为前提。

**（1）接口响应时间**

- **常规业务接口**（不涉及大模型推理的同步请求，如登录、岗位列表与详情、简历维护、任务状态查询等）：在局域网或演示环境同区域部署条件下，**95%** 请求的端到端响应时间 **≤ 500 ms**。
- **大模型类请求**（岗位能力说明生成、学生能力画像生成、人岗匹配说明、报告生成、对话回复等）：单次 **非流式** 调用须在 **≤ 60 s** 内返回可解析业务结果或明确失败；**流式** 输出首包（首字/首段）延迟 **≤ 10 s**。外部服务异常时返回可读错误，不计入成功样本统计。

**（2）页面与交互**

- 首屏关键内容在常见带宽下 **≤ 3 s** 可交互（不含用户网络极差情况）；路由切换宜在 **1 s** 内完成骨架与主数据展示（以前端性能预算与实现为准）。

**（3）批量与异步**

- 岗位列表分页查询在万级数据规模下仍满足上述常规接口指标；个人知识库 **向量化、批量嵌入** 等长耗时任务采用异步执行，接口须及时返回任务标识，用户可在 **合理轮询间隔**下查询状态，避免阻塞 HTTP 连接过久。

**（4）并发能力**

- 演示与验收场景下，支持 **不少于 10 个** 并发在线用户同时使用核心功能（浏览岗位、维护简历、触发匹配或报告、对话等）时，系统无连续不可用；核心接口错误率在 **§2.4 S3** 约定范围内（外部依赖明确不可用除外）。

## 4.4 界面需求

### 4.4.1 整体界面设计规范

项目前端基于Vue3架构与Soybean Admin进行开发，旨在打造高可用、现代化且符合人机交互直觉的Web界面。

（1）视觉基调与国际化化：系统接入 i18n 国际化方案，支持中文与英文环境的无缝切换，为未来扩充更多语种奠定了底层架构基础。此外，系统内置完善的主题切换机制，支持深色模式与浅色模式，以适应不同光照环境下用户的视觉需求。

（2）色彩规范：摒弃传统系统单一的主色限制，系统开放了主色调的自定义权限。用户可根据个人审美偏好自由调整系统主色调，提升产品的个性化与用户黏性。 为保证信息传递的准确性与系统的专业严谨度，界面的语义色保持全局统一不变，用于全局的状态提示与校验反馈。

（3）排版与无障碍设计：采用无衬线字体栈，建立严格的字号层级，确保界面的信息可读性。界面的色彩对比度设计参考 WCAG 标准，确保即使在用户自定义主色调的情况下，核心文字与背景的对比度依然清晰易读。

### 4.4.2 全局布局与导航框架

系统采用模块化的流式布局，保证各个功能区边界清晰，操作动线合理。

（1）侧边栏导航：左侧为系统主导航，提供知识库、简历管理、AI对话等一级功能入口。支持平滑折叠与展开：在进行简历编辑等需要宽屏视野的操作时，可收起侧边栏以最大化操作区面积。

（2）顶部导航栏：面包屑导航实时显示用户当前所处的页面层级，支持点击快速跳转，防止用户在深层级页面中迷失；全局操作区预留深浅色模式切换、消息通知中心、用户个人中心等。

（3）主内容区：采用独立滚动机制，确保在内容过长时，侧边栏和顶部导航栏保持固定，方便用户随时切换功能。页面切换加入Vue3的轻量级过渡动画，消除生硬的视觉闪烁。

## 4.5 接口需求

### 4.5.1 硬件接口

本系统为 Web 应用，**不涉及与专用硬件设备的直接接口**（无串口、总线、驱动级对接等）。运行所依赖的终端、服务器与网络条件见 **§2.3 运行环境**，不在本节单独定义硬件接口规范。

### 4.5.2 软件接口

软件接口分为 **系统对外提供的业务接口**、**系统内部层次接口** 与 **对外部第三方服务的依赖接口** 三类。数据交换以 **UTF-8 编码** 为原则；业务接口以 **HTTPS** 传输、**JSON** 作为请求与响应主体的数据格式（文件上传下载除外）；身份校验采用 **约定请求头携带访问令牌** 等方式，具体字段与安全要求在接口设计说明书与概要设计中细化。

| 人岗匹配与报告类 | 匹配计算、报告生成、润色、完整性检查、保存与导出 | HTTPS；JSON；导出可为文件流或临时下载链接，须约定内容类型与文件名             |
| 对话类      | 会话列表、消息发送与历史查询           | HTTPS；JSON；流式回复可采用服务端推送相关标准机制（以实现为准），须约定连接超时与中断处理 |
| 个人知识库类   | 文档管理、向量化任务状态查询           | HTTPS；JSON；大文件与异步任务状态须单独约定                        |


**通用约定**：统一错误码与错误信息结构；幂等键用于关键写操作（可选）；接口版本可通过路径前缀或请求头区分，避免破坏性变更影响评审环境。

#### （2）系统内部层次接口


| 接口层次     | 说明                                           |
| -------- | -------------------------------------------- |
| 表现层与领域层  | 前端与后端之间仅通过上述 HTTP 接口交互，不绕过服务端直连数据库。          |
| 应用服务与持久化 | 服务端内部通过数据访问组件访问关系型数据库；事务边界由应用服务声明。           |
| 缓存       | 服务端通过缓存客户端访问内存型缓存服务，键命名与 TTL 须规范，避免与业务主键冲突。  |
| 异步任务     | 向量化、批量生成等通过应用内异步执行器或消息机制触发，任务状态持久化，供前端轮询或订阅。 |


#### （3）外部第三方软件与服务接口


| 对接对象       | 用途                               | 规范与约束要点                                                          |
| ---------- | -------------------------------- | ---------------------------------------------------------------- |
| 关系型数据库     | 业务数据、会话记忆、部分结构化配置持久化             | 标准数据库访问协议；库表编码 UTF-8；须启用连接池与超时；生产环境须限制访问网络范围。                    |
| 向量存储能力     | 与关系型数据库同引擎扩展或等价方案，存储嵌入向量与相似检索    | 与业务库协同备份与迁移策略；向量维度与模型输出一致。                                       |
| 内存型缓存      | 会话、验证码、热点数据                      | 标准缓存协议；键过期策略明确；禁止将大体积模型原文长期放入缓存。                                 |
| 对象存储服务     | 用户上传文件、导出物暂存等                    | HTTPS 访问；服务端持有密钥，通过临时凭证或预签名 URL 控制前端直传或下载时效；桶权限最小化。              |
| 大语言模型与嵌入服务 | 岗位能力说明、学生画像、匹配解释、报告生成、查询改写、文本嵌入等 | 由云厂商或开放平台提供的**HTTPS API**；请求须脱敏与限长；须配置重试、熔断与超时；密钥仅存于安全配置，不得写入前端。 |
| 邮件服务（若启用）  | 注册或重置密码等验证码发送                    | SMTP 或云厂商邮件 API；须限制发送频率；模板与发件人合规。                                |


#### （4）数据格式与安全约束

- **字符与日期时间**：统一 UTF-8 编码；日期时间建议采用 ISO 8601 或带时区的字符串，避免歧义。
- **大文本与二进制**：大文本走 JSON 字段须限制最大长度；二进制文件不走 JSON 内嵌，采用 multipart 上传或对象存储。
- **敏感字段**：口令、令牌、密钥不出现在 URL 明文与日志正文；接口响应中不返回内部堆栈。
- **兼容性**：第三方服务接口版本变更时，须在集成层封装适配，避免业务层散落协议细节。

## 4.6 其他需求

本节规定除功能、性能、接口与界面以外的 **非功能性需求**，作为设计、实现与验收的共同依据。

### 4.6.1 安全性

- **身份与访问控制**：所有业务接口须在鉴权通过后方可访问；会话与令牌具备有效期与失效策略；禁止越权访问他人简历、画像、报告与对话记录。
- **输入与输出**：对用户输入与上传文件实施类型、大小与长度限制，防范常见注入与滥用；错误响应不返回内部堆栈与路径细节。
- **日志与审计**：记录必要的安全与操作审计信息时，对身份证号、手机号等敏感字段脱敏；日志保留周期可配置。

### 4.6.2 易用性与无障碍

- **交互一致性**：同类操作控件位置、文案风格与成功/失败反馈方式保持一致；长流程提供步骤提示与可返回上一步能力。
- **可读性**：关键页面支持中文为主、英文为辅；错误提示说明原因与建议操作，避免仅显示错误码。
- **无障碍**：主要操作可通过键盘、鼠标完成；重要图表或状态提供文字说明。

### 4.6.3 可维护性

- **结构清晰**：前后端分层、模块边界明确；业务规则与外部服务协议集中在适配层，便于替换模型或存储实现。
- **可观测**：提供健康检查、分级日志与必要指标，支撑问题定位；关键配置外部化，环境差异通过配置区分。
- **文档与版本**：接口说明、部署说明与重要配置变更纳入版本管理；发布说明记录兼容性变更与回滚要点。

### 4.6.4 可扩展性与兼容性

- **数据与业务扩展**：预留岗位类目扩展、报告模板扩展及可选插件式能力（如新增一种知识库文档类型）的扩展点，避免硬编码魔法常量散落。
- **技术兼容**：数据库与中间件版本升级须在预发环境验证；前端兼容 **§2.3** 所列浏览器近两个大版本。

### 4.6.5 可靠性与容错

- **可用性目标**：核心接口在正常运行期错误率满足 **§2.4 S3**；对外部依赖失败须熔断、超时与友好提示，避免线程与连接耗尽。
- **数据一致性**：关键写操作具备事务或补偿策略；异步任务支持重试与幂等，避免重复写入导致脏数据。
- **备份与恢复**：数据库与重要配置须制定备份周期与恢复演练要求（周期由运维约定，至少满足演示数据可恢复）。

### 4.6.6 合规与隐私

- **个人信息**：收集、使用简历与行为数据须符合用户告知与同意的范围；演示与评测使用脱敏或合成数据。
- **赛事与开源**：若使用第三方库与数据须保留许可证与来源说明；提交材料不侵犯他人著作权与商业秘密。

# 5 概要设计

## 5.1 处理流程

系统围绕“岗位认知—能力建模—匹配决策—报告输出—持续优化”的主线运行，核心处理流程如下：

1. 用户进入系统并完成注册/登录，服务端通过鉴权组件校验身份，初始化用户会话。
2. 用户可先浏览岗位列表与岗位详情，系统基于岗位原始字段与岗位能力说明结果，提供岗位理解入口。
3. 用户完善简历与经历信息（教育、任职、项目、技能），或上传材料触发能力解析流程，生成学生就业能力画像。
4. 当用户选择目标岗位后，系统读取“岗位侧能力说明 + 学生侧能力画像”，在四维能力框架下执行人岗匹配计算，并输出综合结论及差距说明。
5. 系统基于匹配结果与用户意向生成职业生涯发展报告，报告支持润色、完整性检查、人工编辑与导出。
6. 用户可在智能对话中继续追问岗位、项目与规划建议；系统结合历史会话与知识库检索结果进行上下文增强回答，形成“反馈—修订—再生成”的闭环。

## 5.2 总体结构设计

系统采用前后端分离架构，后端以 Spring Boot 为核心，围绕业务域划分模块并统一对外提供 REST API。

### （1）总体架构分层

- 表现层：Web 前端负责页面渲染、表单交互、结果展示与导出触发。
- 接口层：后端 Controller 统一接收请求、执行参数校验、返回标准响应。
- 业务层：按领域划分为用户认证、岗位、简历、能力画像、匹配报告、知识库、对话等服务。
- 基础设施层：PostgreSQL（含 pgvector）负责关系数据与向量数据存储，Redis 负责缓存与验证码，COS 负责对象存储，DashScope 提供大模型与嵌入能力。

### （2）后端模块划分

- 用户认证模块：负责注册登录、验证码校验、令牌签发与鉴权。
- 岗位与岗位能力模块：负责岗位查询、岗位能力信息抽取与说明管理。
- 简历与学生画像模块：负责教育/任职/项目/技能维护与学生能力画像生成。
- 对话模块：负责会话管理、消息存储与多轮交互。
- 知识库模块：负责知识库管理、文档解析、向量化与检索增强。
- 通用支撑模块：负责安全配置、模型接入、对象存储、缓存与公共能力封装。

## 5.3 功能设计

本节给出核心功能在概要层面的职责边界与协作关系：

1. 账户与权限管理：提供注册、登录、验证码校验、令牌签发与访问控制；对核心业务接口进行用户身份隔离。
2. 岗位浏览与能力说明：支持岗位列表检索与详情查看；对岗位描述进行结构化抽取，形成岗位能力说明供后续匹配使用。岗位画像覆盖不少于 10 个就业岗位，并统一覆盖专业技能、证书要求、创新能力、学习能力、抗压能力、沟通能力、实践能力等维度。
3. 简历维护与学生能力画像：用户维护教育、经历、项目、技能信息；系统结合模型能力生成多维学生画像，并输出完整度与竞争力结果。学生画像维度与岗位画像维度保持一致，确保可对齐匹配。
4. 人岗匹配与报告生成：按基础要求、职业技能、职业素养、发展潜力四维执行匹配评分，生成可解释结论；在此基础上生成职业发展报告，覆盖职业探索与岗位匹配、职业目标设定与职业路径规划、分阶段行动计划与评估指标。
5. 知识库与智能对话：用户材料经解析与向量化后进入个人知识库；对话时执行检索增强，提升回答针对性与上下文一致性。
6. 岗位关联图谱：构建垂直岗位图谱与换岗路径图谱。垂直图谱覆盖岗位描述与晋升路径关联；换岗图谱覆盖相关岗位血缘关系，至少支持 5 个岗位的换岗路径展示，且每个岗位不少于 2 条换岗路径。
7. 报告编辑优化与导出：支持报告智能润色、完整性检查、手动编辑调整与一键导出，确保报告可直接用于展示与提交。
8. 文件上传与导出支撑：统一通过对象存储处理文件上传、访问与导出下载，降低应用层二进制处理复杂度。

模块关联关系上，岗位能力说明与学生能力画像是人岗匹配的双输入；岗位关联图谱与匹配结果共同构成职业报告生成依据；报告生成结果再进入编辑优化与导出链路；知识库检索为对话与内容优化提供增强上下文。

## 5.4 数据流转设计

系统数据流转遵循“采集—校验—处理—存储—复用”原则，关键链路如下：

- 岗位数据链路：岗位原始数据入库后，由岗位能力说明流程生成结构化岗位画像并落库；岗位画像按统一维度覆盖不少于 10 个岗位类别；匹配与报告阶段按岗位标识回读。
- 用户履历链路：用户录入或上传履历材料后，经后端校验与结构化存储，作为学生能力画像生成输入。
- 图谱构建链路：基于岗位数据与岗位画像构建垂直晋升图谱与换岗路径图谱，输出可查询路径数据并执行覆盖度校验。
- 匹配报告链路：人岗匹配服务读取岗位画像与学生画像，生成四维得分与综合结论；报告服务同时读取岗位图谱结果，输出“匹配结论 + 目标路径 + 行动计划 + 评估指标”的完整报告并保存版本。
- 报告优化链路：报告初稿生成后，执行智能润色与完整性检查；用户可手动编辑并生成最终可导出版本。
- 知识库链路：用户上传文档后完成文本抽取、分块与向量化写入，检索时按用户隔离检索相关片段并注入对话上下文。
- 对话链路：消息写入会话存储，同时结合检索结果与模型推理输出回答，形成可追溯交互记录。

数据流转中，所有跨模块调用均通过服务层接口完成，避免前端直接访问底层存储。

## 5.5 用户界面设计

界面设计以“低学习成本 + 明确决策路径”为目标，整体沿用前文约定的模块化布局与响应式策略。

### （1）页面结构与导航

- 首页/工作台：展示核心入口与最近处理记录。
- 岗位中心：岗位检索、详情、岗位能力说明、垂直晋升路径与换岗路径展示。
- 简历与能力中心：教育、经历、项目、技能维护及能力画像查看。
- 匹配与报告中心：人岗匹配分析结果、职业探索结论、目标路径规划、行动计划、报告润色检查、编辑与导出。
- 知识库与对话中心：知识文档管理、向量化状态、智能对话。

### （2）页面跳转逻辑

用户通常按“岗位浏览与图谱查看 → 简历完善 → 学生画像生成 → 人岗匹配 → 职业报告生成 → 报告优化与导出 → 对话优化”的路径操作。系统在关键节点提供前置校验与引导（如画像缺失时跳转补全页、图谱缺失时提示先构建图谱），避免无效操作。

### （3）交互原则

- 关键操作提供显式反馈（处理中、成功、失败）。
- 长耗时流程采用异步任务或分段提示，避免界面阻塞。
- 报告与匹配结果支持可解释展示，便于用户理解结果来源与改进方向。

## 5.6 数据结构设计

核心数据结构围绕“用户—岗位—画像—匹配—报告—知识—对话”七类对象组织，关系概述如下：

1. 用户与账户：以用户主键为中心，关联登录凭据、会话与安全校验信息。
2. 岗位与岗位能力：岗位主数据与岗位能力说明一对一或一对多版本关系，用于支撑岗位理解与匹配输入。
3. 学生履历与学生画像：教育、任职、项目、技能等子表与用户关联；画像表聚合多维能力及评分字段。
4. 岗位关联图谱：岗位节点、垂直关系、换岗关系与路径校验结果组成图谱数据对象，用于路径查询与报告引用。
5. 人岗匹配与报告：匹配记录关联用户与目标岗位，保存四维得分、权重与综合结论；报告记录关联匹配结果与图谱路径结果，支持润色、完整性检查、编辑与版本化。
6. 知识库与文档向量：知识库主表、文档元数据表与向量分块表关联；向量数据与用户隔离存储，保障检索边界。
7. 会话与消息：会话表关联用户，消息表按会话维度顺序保存，支持多轮上下文恢复。

具体字段、约束与索引策略在第六章数据库设计中展开。

## 5.7 接口设计

### 5.7.1 外部接口

外部接口分为“前后端业务接口”与“第三方服务接口”两类：

1. 前后端业务接口：
  - 统一采用约定的 API 路径前缀。
  - 传输协议：HTTPS（开发环境可本地 HTTP 调试）。
  - 数据格式：JSON；文件场景采用 multipart 或对象存储临时链接。
  - 安全机制：JWT 鉴权 + 用户数据隔离 + 统一错误响应结构。
2. 第三方服务接口：
  - DashScope：用于对话、内容生成与嵌入向量生成。
  - 腾讯云 COS：用于文件上传与访问。
  - Redis 与 PostgreSQL：作为基础设施由后端统一访问，不直接暴露给前端。

接口治理遵循版本可扩展、错误码统一、超时可回退的设计原则。

### 5.7.2 内部接口

内部接口采用“Controller → Service → Mapper/Repository”分层调用模式：

- Controller 层负责请求入参校验、鉴权上下文读取、统一响应封装。
- Service 层负责业务编排与领域规则实现，是跨模块协作的主要入口。
- Mapper/Repository 层负责持久化操作与查询封装。
- AI 适配层负责模型调用、提示词组织、响应解析与结构化校验。

内部接口约束：

1. 入参与出参对象使用明确 DTO/VO，避免直接暴露持久化实体。
2. 长耗时能力（向量化、批量生成）优先异步化并提供状态查询接口。
3. 对外部依赖调用统一封装，避免业务代码散落供应商协议细节。

## 5.8 错误/异常处理设计

### 5.8.1 错误/异常输出信息

系统采用“用户可理解 + 开发可定位”的双层错误输出策略：

- 用户侧：返回统一业务错误码、简要错误描述与建议操作（如重试、补全信息、稍后再试）。
- 服务侧：记录结构化日志（时间、请求标识、用户标识、模块、异常类型、堆栈摘要）。
- 安全侧：敏感信息脱敏输出，不在响应或日志中暴露密钥、令牌、明文密码等内容。
- 外部依赖失败：明确区分“模型服务异常”“存储服务异常”“网络超时”等类别，避免笼统报错。

### 5.8.2 错误/异常处理对策

针对不同异常类型，系统采用分级处理机制：

1. 参数与业务校验异常：快速失败并返回明确字段级提示，不进入下游耗时流程。
2. 鉴权与权限异常：统一拦截，返回未授权/无权限结果，阻断越权访问。
3. 外部服务超时或失败：设置超时、限流与重试边界；失败时返回可理解提示并保留已完成数据。
4. 数据一致性异常：关键写流程采用事务控制；异步任务采用幂等策略，避免重复写入。
5. 系统级异常：统一异常处理器兜底并记录日志，确保接口响应可预测。

## 5.9 系统配置策略

系统配置采用“分环境配置 + 环境变量注入”的策略：

- 基础配置：数据库、缓存、模型、对象存储、接口前缀等在配置文件集中管理。
- 敏感配置：模型密钥、存储密钥、数据库口令等通过环境变量注入，避免硬编码入库。
- 环境区分：本地开发、测试演示、生产部署按配置文件与变量组合区分。
- 可观测配置：日志级别、健康检查暴露项可按环境调节，兼顾调试效率与运行安全。

## 5.10 系统部署方案

系统采用容器化部署方案，支持快速复现与环境一致性：

1. 基础组件部署：通过 Docker Compose 拉起 PostgreSQL（含 pgvector）与 Redis。
2. 应用服务部署：后端服务基于 Dockerfile 构建镜像并启动，端口按约定映射。
3. 配置注入：通过运行时配置与环境变量注入数据库、缓存、模型与对象存储参数。
4. 发布流程：代码合并后通过 CI/CD 流水线执行构建、镜像发布与部署更新。
5. 运维保障：通过健康检查接口与基础日志监控服务状态，故障时支持快速重启与回滚。

## 5.11 其他相关技术与方案

除核心业务设计外，系统还采用以下关键技术方案增强可用性与可扩展性：

1. RAG 机制：通过文档切分、向量检索与上下文拼装提升对话与分析的相关性。
2. 提示词模板化：将岗位解析、画像生成、匹配说明等场景模板化，降低输出波动。
3. 类型处理与结构化存储：结合 JSON/JSONB 处理能力保存复杂结构结果，提升查询与演进弹性。
4. 安全基线：统一鉴权、跨域策略与输入校验，降低常见安全风险。
5. 模块化演进：以服务域划分边界，为后续新增评测、推荐或多模型切换提供扩展空间。

# 6 数据库设计

## 6.1 设计目标与原则

数据库设计以“结构化主数据 + 半结构化扩展数据 + 向量检索数据”协同为核心，服务于岗位认知、能力画像、人岗匹配、职业报告、知识库检索与智能对话等核心流程。总体遵循以下原则：

1. 一体化存储：统一采用 PostgreSQL 承载关系数据、JSONB 数据与向量数据，降低多存储系统运维复杂度。
2. 用户隔离：核心业务表均以用户标识作为数据边界，保障多用户场景下的数据安全与查询可控。
3. 可扩展表达：复杂业务对象优先采用 JSONB 存储结构化扩展字段，减少高频迭代导致的表结构震荡。
4. 性能优先：围绕高频查询路径建设组合索引，并对语义检索场景使用向量索引与模糊检索索引。
5. 工程可维护：通过统一时间字段、枚举编码与命名规则，提升数据治理与跨模块协作效率。

## 6.2 数据库总体结构

按业务域划分，数据库由 6 组核心数据域构成：

1. 用户域：用户账号、用户画像、行为日志。
2. 简历域：教育经历、技能清单、实习/工作经历、项目经历、简历与专用简历、人岗结果关联。
3. 岗位域：岗位信息、公司信息、岗位能力画像。
4. 知识库域：知识库、知识文档、向量分块、向量化任务。
5. 对话域：会话、消息、会话记忆。
6. 通用扩展域：向量检索与半结构化元数据（JSONB）支撑字段。

## 6.4 关系设计与一致性策略

本项目采用“逻辑外键 + 应用层约束校验”策略：即在字段层保留明确关联语义，在业务层完成关联存在性与权限校验。该方案可降低跨域事务耦合，提升批量导入、异步任务与演示环境迁移的执行稳定性。

典型逻辑关联包括：

1. 用户与画像/简历/知识库/会话的一对多或一对一关系。
2. 岗位与岗位能力画像的一对多关系。
3. 知识库与文档、文档与向量分块的一对多关系。
4. 会话与消息的一对多关系。
5. 简历与专用简历、人岗结果之间的关联关系。

## 6.5 索引设计

索引设计围绕“高频过滤、时间排序、模糊匹配、向量相似检索”四类场景展开：

1. 常规查询索引：在用户标识、状态字段、时间字段上建立单列/组合索引，提升列表与筛选性能。
2. 唯一性索引：对账号标识、业务去重字段、知识库与文档关键组合建立唯一索引，防止重复写入。
3. 模糊检索索引：针对公司名称等文本检索场景建立三元组索引，提升模糊匹配效率。
4. 向量检索索引：在岗位向量字段与知识分块向量字段上建立 HNSW 索引，支撑语义召回与 RAG 场景。

## 6.6 字段规范与编码约定

1. 主键统一采用 BIGSERIAL，自增生成，便于跨模块主数据关联。
2. 时间字段统一采用 TIMESTAMP，默认值为当前时间，满足审计与排序需求。
3. 枚举字段统一采用 SMALLINT 存储，具体语义由业务字典管理。
4. 可变结构字段优先采用 JSONB（如技能清单、画像明细、文档元数据），兼顾灵活性与查询能力。
5. 向量字段统一采用 1024 维，确保检索模型与向量表维度一致。

## 6.7 存储过程、触发器与任务机制

当前版本不依赖数据库存储过程与触发器实现核心业务逻辑，主要业务规则在应用服务层实现。数据库侧重点为：

1. 提供稳定的数据持久化与索引检索能力。
2. 通过默认值、唯一索引与检查约束保证基础数据质量。
3. 通过任务表记录异步向量化过程状态，实现失败重试与过程审计。

## 6.8 数据安全与运维策略

1. 安全隔离：以用户标识为查询边界，防止跨用户数据访问。
2. 敏感保护：账号凭据使用加密存储，日志与导出过程遵循脱敏原则。
3. 备份恢复：按库级与表级制定备份策略，支持演示与验收数据快速恢复。
4. 初始化策略：数据库初始化脚本包含扩展安装、表结构创建与索引创建，保证环境可重复部署。

## 6.9 小结

本章数据库设计已完整覆盖用户管理、简历与画像、岗位与企业、知识库向量检索、智能对话记忆等核心场景，能够稳定支撑“岗位关联分析 + 学生职业生涯发展报告 + 对话式持续优化”的业务闭环，并满足后续性能优化与功能扩展需求。

# 7 核心功能模块

## 7.1 岗位模块（含岗位画像分析）

### 7.1.1 功能描述

岗位模块用于承载岗位数据查询、岗位信息理解、岗位关系展示与岗位画像分析能力，是用户进行职业探索与目标岗位决策的核心入口。模块围绕“岗位信息结构化 + 能力要求可解释 + 路径关系可视化”展开，支持从单一岗位浏览扩展到岗位能力与职业路径联动分析。

模块目标如下：

1. 支持岗位列表检索、筛选与详情查看，帮助用户快速定位目标岗位。
2. 支持岗位画像分析，输出岗位在专业技能与综合素养维度上的能力要求摘要。
3. 支持岗位纵向发展与横向迁移关系展示，为职业路径规划提供决策依据。
4. 支持岗位信息与后续人岗匹配、职业报告模块联动，形成一致的岗位侧输入标准。

### 7.1.2 输入

岗位模块输入来源于岗位检索页面、岗位详情页面与岗位画像分析触发操作，输入内容如下：


| 输入项    | 业务说明                  | 约束要求           |
| ------ | --------------------- | -------------- |
| 检索关键词  | 岗位名称、技能关键词、公司关键词等检索条件 | 可选，长度与字符类型合法   |
| 筛选条件   | 地点、薪资区间、岗位类别、企业属性等筛选项 | 可多选，取值需在约定范围内  |
| 排序条件   | 按时间、相关度或综合权重排序        | 可选，必须属于支持的排序类型 |
| 岗位标识   | 指定查询或分析的目标岗位          | 必填，需对应有效岗位记录   |
| 画像分析请求 | 触发岗位能力画像生成或刷新         | 触发时需具备可用岗位内容数据 |


触发条件为用户提交岗位检索请求、进入岗位详情页，或主动发起岗位画像分析。

### 7.1.3 输出

岗位模块输出按查询或分析场景返回以下结果：


| 输出项    | 业务说明                  | 返回时机   |
| ------ | --------------------- | ------ |
| 岗位列表数据 | 满足检索条件的岗位集合及摘要信息      | 列表查询成功 |
| 岗位详情数据 | 单岗位的职责、要求、薪资、企业等完整信息  | 详情查询成功 |
| 岗位画像结果 | 岗位能力要求、关键优势项、缺失项与总结说明 | 画像分析成功 |
| 岗位路径信息 | 纵向发展路径与横向迁移路径结果       | 路径查询成功 |
| 业务错误码  | 失败场景下的标准错误标识          | 操作失败   |
| 错误提示信息 | 面向用户的可读错误说明           | 操作失败   |


输出结果保持结构化与可解释，支持直接用于后续匹配分析与职业报告生成。

### 7.1.4 程序逻辑

岗位模块处理流程如下：

1. 接收检索、详情、路径或画像分析请求，并执行参数校验与格式规范化。
2. 根据查询条件执行岗位数据检索，返回分页列表或目标岗位详情。
3. 当用户进入岗位分析流程时，读取岗位职责与要求信息，执行岗位画像分析并生成结构化结果。
4. 基于岗位关系数据组织纵向晋升路径与横向迁移路径，输出可展示的路径集合。
5. 将岗位画像结果与岗位基础信息统一封装返回，供前端展示与后续业务引用。
6. 在查询与分析完成后记录关键操作日志，支持结果追踪与质量复盘。

异常分支处理：

- 查询条件不合法：返回参数错误并提示修正条件。
- 岗位记录不存在：返回资源不存在提示并终止后续分析。
- 画像分析失败：返回分析失败提示并保留原始岗位数据可浏览能力。
- 路径数据缺失：返回可读提示并允许用户继续查看岗位详情信息。

### 7.1.5 限制条件

1. 岗位画像分析依赖岗位文本内容质量，输入信息过少会影响分析完整度。
2. 岗位路径结果受当前岗位库覆盖范围影响，未覆盖岗位不参与路径计算。
3. 岗位模块输出为岗位侧结论，不直接替代学生侧能力评估与人岗最终结论。
4. 同一岗位在短时间内重复触发分析时应受频控策略约束，避免不必要的资源消耗。

| 缺失能力项  | 当前尚未充分体现的关键能力项  | 画像生成成功 |
| 改进建议   | 面向短期提升的可执行建议清单  | 画像生成成功 |
| 业务错误码  | 失败场景下的标准错误标识    | 操作失败   |
| 错误提示信息 | 面向用户的可读错误说明     | 操作失败   |


输出结果保持结构化与可解释，可直接用于人岗匹配和职业规划报告生成。

### 7.2.4 程序逻辑

学生就业能力画像模块处理流程如下：

1. 接收画像生成请求并校验用户身份、输入参数与数据完整性。
2. 汇总用户履历主数据与补充描述信息，构建画像分析输入上下文。
3. 按统一能力维度对输入信息进行拆解、归纳与证据提取，形成能力维度草案。
4. 执行评分计算，生成完整度评分、竞争力评分与分项评分明细。
5. 结合评分结果输出缺失能力项与改进建议，并生成结构化画像结果。
6. 持久化画像记录并返回结果，供匹配分析与报告模块复用。

异常分支处理：

- 输入信息缺失或质量不足：返回提示并引导用户补全关键履历信息。
- 画像生成失败：返回分析失败提示，并保留历史可用画像供查看。
- 评分计算异常：返回系统处理失败提示并记录异常日志。
- 数据写入失败：返回保存失败提示，避免前端误判为成功状态。

### 7.2.5 限制条件

1. 画像结果依赖用户履历信息真实性与完整度，输入质量会直接影响结果可信度。
2. 当用户目标岗位方向未明确时，系统以通用策略生成画像，专项结论精度可能降低。
3. 画像评分为辅助决策结果，不应单独作为录用判断依据。
4. 同一用户短时间内重复触发画像生成应受调用频控约束，避免资源浪费。

## 7.4 岗位关联图谱模块

### 7.4.1 功能描述

岗位关联图谱模块用于落实赛题中“建立岗位间关联图谱”的要求，核心目标是让用户清晰理解岗位未来发展路径。模块设计严格覆盖两类图谱能力：垂直岗位图谱与换岗路径图谱，并提供可核验的覆盖标准。

模块目标如下：

1. 构建垂直岗位图谱，完整呈现岗位描述、岗位层级关系与岗位晋升路径关联信息。
2. 构建换岗路径图谱，建立相关岗位之间的血缘关系与迁移关系，支持路径规划。
3. 在样本覆盖层面，至少输出 5 个代表性岗位的换岗路径结果，且每个岗位不少于 2 条换岗路径。
4. 将图谱结果作为职业路径规划与职业生涯报告的输入依据，支撑后续行动计划设计。
5. 输出结果需具备可解释性，能够说明“为何可以晋升/为何可以换岗”的关系依据。

### 7.4.2 输入

岗位关联图谱模块输入来源于岗位主数据、岗位画像结果与图谱构建规则，输入内容如下：


| 输入项     | 业务说明                           | 约束要求             |
| ------- | ------------------------------ | ---------------- |
| 岗位基础数据集 | 包含岗位名称、职位描述、岗位编码、行业、企业属性等岗位主数据 | 需满足数据完整性与字段一致性要求 |
| 岗位画像信息  | 岗位能力维度、关键技能、岗位特征摘要等结构化结果       | 与岗位主数据一一对应       |
| 垂直关系规则  | 岗位层级定义、晋升方向约束、同序列岗位映射规则        | 规则需可配置且可追溯       |
| 换岗关系规则  | 岗位能力相似度规则、跨岗位血缘规则、迁移门槛规则       | 规则需可解释并可审计       |
| 图谱构建请求  | 全量构建或增量更新的图谱任务请求               | 必须明确构建范围与版本号     |
| 路径查询请求  | 指定起点岗位、目标方向、路径条数与深度约束          | 查询条件必须合法且边界清晰    |


触发条件为系统发起图谱构建任务，或用户在职业规划场景发起路径查询。

### 7.4.3 输出

岗位关联图谱模块输出按“图谱构建结果”和“路径查询结果”两类场景返回如下内容：


| 输出项      | 业务说明                           | 返回时机   |
| -------- | ------------------------------ | ------ |
| 垂直图谱结果   | 包含岗位描述、岗位层级、晋升路径关系的图谱数据        | 图谱构建成功 |
| 换岗图谱结果   | 包含岗位血缘关系、可迁移岗位及迁移方向的图谱数据       | 图谱构建成功 |
| 覆盖校验结果   | 至少 5 个岗位、每岗位不少于 2 条换岗路径的达标校验信息 | 图谱构建成功 |
| 垂直路径查询结果 | 指定岗位的晋升路径集合与阶段说明               | 查询成功   |
| 换岗路径查询结果 | 指定岗位的换岗路径集合与路径说明               | 查询成功   |
| 路径解释信息   | 路径形成依据、能力衔接点、建议迁移顺序说明          | 查询成功   |
| 业务错误码    | 失败场景下的标准错误标识                   | 操作失败   |
| 错误提示信息   | 面向用户的可读错误说明                    | 操作失败   |


输出结果需满足结构化、可解释、可核验要求，能够直接用于职业路径规划与报告生成。

### 7.4.4 程序逻辑

岗位关联图谱模块设计流程如下：

1. 接收图谱构建请求，校验岗位数据质量、规则配置完整性与版本信息。
2. 对岗位数据执行标准化处理，统一岗位名称、岗位类别与能力标签表达。
3. 根据垂直关系规则生成岗位晋升链路，形成垂直岗位图谱结果。
4. 根据换岗关系规则计算岗位血缘关系与迁移关系，形成换岗路径图谱结果。
5. 对图谱结果执行去重与冲突校验，并进行覆盖度校验，确认“至少 5 个岗位、每岗位至少 2 条换岗路径”达标。
6. 在查询阶段按用户输入返回垂直路径与换岗路径，并附带路径解释信息。
7. 将路径结果输出给职业规划与报告模块，作为目标设定与行动计划的依据。

异常分支处理：

- 岗位数据缺失或异常：返回前置数据不足提示并终止构图任务。
- 规则配置冲突：返回规则冲突提示并输出冲突项说明。
- 覆盖度不达标：返回达标校验失败提示，并标记未达标岗位与缺失路径数。
- 路径不可达：返回无可用路径提示，并提供相近岗位方向建议。
- 构图任务失败：返回失败状态并保留最近稳定图谱版本用于查询。

### 7.4.5 限制条件

1. 本模块当前为设计方案，尚未完成线上功能实现与正式验收。
2. 图谱质量高度依赖岗位数据覆盖度与岗位画像质量，数据稀疏时路径稳定性会下降。
3. 换岗路径与晋升路径属于决策辅助信息，不等同于实际就业结果承诺。
4. 当岗位分布不均衡时，部分岗位可能暂时无法生成足量高置信路径。
5. 图谱构建建议采用异步任务执行模式，避免全量计算阻塞在线查询链路。

| 简历标识   | 当前简历对象标识       | 简历保存成功    |
| 简历名称   | 当前简历展示名称       | 简历保存或查询成功 |
| 分项汇总信息 | 各履历分项的数量与状态摘要  | 查询或保存成功   |
| 业务错误码  | 操作失败时的标准错误标识   | 操作失败      |
| 错误提示信息 | 面向用户的可读错误说明    | 操作失败      |


输出信息保持结构化与可追溯，便于后续画像与匹配流程复用。

### 8.2.4 程序逻辑

简历编辑模块处理流程如下：

1. 接收前端提交的履历或简历编排请求，并进行参数合法性校验。
2. 校验用户身份与数据归属，确保仅允许操作本人履历数据。
3. 根据操作类型执行新增、更新、删除或查询，并同步维护更新时间戳。
4. 当执行简历编排保存时，校验简历名称唯一性与条目存在性，完成简历聚合写入。
5. 当执行岗位定制操作时，基于原始简历生成专用简历记录，并建立关联映射。
6. 返回操作结果；若写入成功则回传最新结构化数据供前端刷新展示。

异常分支处理：

- 参数不完整或格式不合法：返回参数错误并提示修正项。
- 数据不存在或越权访问：返回无权限或资源不存在提示。
- 简历名称冲突：返回重名错误并提示用户更换名称。
- 数据写入异常：返回系统繁忙提示并记录错误日志。

### 8.2.5 限制条件

1. 用户仅可编辑和查看本人的履历与简历数据，不支持跨用户共享编辑。
2. 简历编排依赖结构化子数据，若关联条目被删除需在保存前完成一致性校验。
3. 含敏感信息的文本输入需经过长度、格式与安全过滤，防止非法注入。
4. 简历编辑结果以保存版本为准，未保存内容不进入后续画像与匹配计算链路。

## 8.3 知识库模块

### 8.3.1 功能描述

知识库模块用于沉淀用户职业规划过程中的资料资产，支持知识库初始化、文档管理、状态跟踪与后续检索增强调用。模块通过“知识库主实体 + 知识文档”双层结构管理用户资料，确保资料可持续维护、可追溯、可复用。

模块目标如下：

1. 支持为用户创建与查询个人知识库，并提供一键清空能力。
2. 支持知识文档分页查询与按标识查询，便于用户管理历史资料。
3. 支持知识文档新增、修改、删除，覆盖资料全生命周期管理。
4. 支持记录文档向量化相关状态信息，为后续检索增强与对话调用提供基础。

### 8.3.2 输入

知识库模块输入来源于知识库管理页面与知识文档管理页面，输入内容如下：


| 输入项     | 业务说明                   | 约束要求                |
| ------- | ---------------------- | ------------------- |
| 知识库操作请求 | 创建知识库、查询知识库、清空知识库等操作请求 | 必须绑定有效用户身份          |
| 文档分页参数  | 页码、每页条数等分页查询参数         | 页码从 1 开始，分页参数在合理范围内 |
| 文档基础信息  | 文档类型、来源内容、标题、元数据信息等    | 关键字段完整，格式合法         |
| 文档标识信息  | 单条文档查询、更新、删除所需的文档标识    | 必须对应有效文档记录          |
| 文档更新请求  | 文档内容或属性更新操作            | 更新目标必须属于当前用户知识库     |


触发条件为用户发起知识库初始化、文档管理或知识库清空操作。

### 8.3.3 输出

知识库模块输出按操作场景返回如下内容：


| 输出项    | 业务说明             | 返回时机       |
| ------ | ---------------- | ---------- |
| 知识库信息  | 当前用户知识库基础信息与状态摘要 | 知识库创建/查询成功 |
| 文档分页结果 | 文档列表、分页信息与文档摘要字段 | 文档列表查询成功   |
| 文档详情结果 | 单条文档完整信息与状态信息    | 文档详情查询成功   |
| 文档操作结果 | 新增、更新、删除后的文档结果信息 | 文档操作成功     |
| 清空结果信息 | 知识库清空操作结果        | 清空成功       |
| 业务错误码  | 失败场景下的标准错误标识     | 操作失败       |
| 错误提示信息 | 面向用户的可读错误说明      | 操作失败       |


输出保持结构化，便于后续检索增强与对话模块直接复用。

### 8.3.4 程序逻辑

知识库模块处理流程如下：

1. 接收知识库或文档操作请求，并执行身份校验与参数合法性校验。
2. 当执行知识库创建或查询时，返回当前用户知识库实体信息。
3. 当执行文档分页查询时，按分页参数返回文档列表及状态摘要。
4. 当执行文档新增或更新时，校验文档字段有效性并写入最新文档记录。
5. 当执行文档删除时，校验归属关系并删除目标文档。
6. 当执行知识库清空时，按用户维度清理关联文档与相关数据，并返回结果。

异常分支处理：

- 参数缺失或格式不合法：返回参数错误并提示修正项。
- 文档不存在或无权限访问：返回资源不存在或无权限提示。
- 数据写入异常：返回系统繁忙提示并记录异常日志。
- 清空操作失败：返回清理失败提示并保留当前可用数据状态。

### 8.3.5 限制条件

1. 知识库与文档严格按用户隔离，不支持跨用户访问与操作。
2. 文档管理依赖输入内容质量，来源信息缺失会影响后续检索效果。
3. 清空知识库属于高影响操作，执行前应进行二次确认。
4. 文档状态信息用于过程追踪，不应替代最终业务结果判断。

## 8.4 AI对话模块

### 8.4.1 功能描述

AI 对话模块用于提供职业规划场景下的多轮问答能力，覆盖会话管理、消息查询、流式回复与中断续传等核心能力。模块通过“会话实体 + 消息流水”组织上下文，使用户能够围绕岗位认知、能力提升与报告优化进行持续交互。

模块目标如下：

1. 支持会话创建、会话查询、标题修改与会话删除等会话管理能力。
2. 支持按会话维度分页查询消息记录，保障历史对话可追溯。
3. 支持流式问答输出，提升长文本生成场景下的交互体验。
4. 支持流式对话中断后续传，增强网络波动场景下的可用性。

### 8.4.2 输入

AI 对话模块输入来源于会话页与聊天页，输入内容如下：


| 输入项    | 业务说明                   | 约束要求         |
| ------ | ---------------------- | ------------ |
| 会话操作请求 | 创建会话、查询会话、修改标题、删除会话等请求 | 必须绑定有效用户身份   |
| 会话标识   | 查询或操作目标会话所需标识          | 必须对应当前用户会话   |
| 标题更新信息 | 新的会话标题内容               | 长度与格式符合约束    |
| 消息查询参数 | 会话标识、页码、每页条数等参数        | 分页参数在合理范围内   |
| 对话消息请求 | 用户问题内容、上下文信息、交互配置等     | 消息内容不能为空     |
| 续传参数   | 流式会话续传标识与续传偏移量         | 续传标识有效且偏移量合法 |


触发条件为用户发起会话管理、消息查询、流式聊天或续传操作。

### 8.4.3 输出

AI 对话模块输出按管理或对话场景返回如下内容：


| 输出项    | 业务说明              | 返回时机   |
| ------ | ----------------- | ------ |
| 会话信息   | 会话创建结果、会话详情或会话列表  | 会话管理成功 |
| 标题更新结果 | 标题修改后的会话结果信息      | 标题修改成功 |
| 消息分页结果 | 会话消息列表及分页信息       | 消息查询成功 |
| 流式回复内容 | 按顺序推送的回答片段数据流     | 流式对话成功 |
| 续传回复内容 | 从指定偏移量恢复后的回答片段数据流 | 续传成功   |
| 业务错误码  | 失败场景下的标准错误标识      | 操作失败   |
| 错误提示信息 | 面向用户的可读错误说明       | 操作失败   |


输出结果保证可追溯与可重放，支持前端展示、断线恢复与会话复盘。

### 8.4.4 程序逻辑

AI 对话模块处理流程如下：

1. 接收会话或消息相关请求并执行身份校验、参数校验。
2. 会话管理请求按操作类型执行会话创建、查询、标题更新或删除。
3. 消息查询请求按会话与分页条件返回历史消息结果。
4. 流式对话请求进入消息处理链路，分段返回模型回复结果。
5. 当发生流式中断时，支持按续传标识与偏移量恢复输出。
6. 在操作完成后记录会话与消息状态，确保历史上下文一致。

异常分支处理：

- 会话不存在或归属不匹配：返回资源不存在或无权限提示。
- 消息参数不合法：返回参数错误并提示修正。
- 流式生成中断：返回中断状态并提供续传入口。
- 续传失败：返回续传失败提示并保留原会话数据。

### 8.4.5 限制条件

1. 会话与消息严格按用户隔离，禁止跨用户访问历史记录。
2. 流式输出受网络质量影响，弱网场景下建议优先使用续传能力。
3. 对话结果属于智能辅助建议，不应替代用户最终职业决策。
4. 长会话场景需控制上下文窗口，避免响应延迟显著上升。
